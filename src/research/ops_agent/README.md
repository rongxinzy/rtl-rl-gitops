# Bounded operations agent

The agent observes infrastructure every minute and persists sanitized status, findings and a bounded audit trail to a dedicated PVC. It uses the exact coordinator `research/brain/providers.py` and the same `rtl-brain/rtl-brain-secrets` model keys; no independent credentials are copied. Background model requests go through the router's authenticated background route. Provider metadata is recorded without response bodies or prompts.

It may replace one persistently unhealthy pod only in `rtl-system/glm-router`, `rtl-system/rtl-operator`, or the isolated `rtl-brain/rtl-ops-recovery-canary`. The deployment must have at least two desired replicas, a completed rollout, a ready peer and matching Deployment → ReplicaSet → Pod owner UIDs. It observes failures continuously for at least ten minutes (canary only may shorten this), rechecks ownership and peer health immediately before deletion, and supplies a UID precondition. Attempts are reserved before execution; uncertain results remain pending until recovery is observed. Per-target cooldown is 30 minutes, recovery budget six attempts/day, model budget 60 calls/day and minimum model interval 15 minutes. Missing observations break failure continuity. State corruption fails closed.

No arbitrary shell, host restart, GPU lifecycle operation, Secret/PVC/database mutation, or evaluation changes are supported. Persistent schedule waits, unhealthy backups, failed/pending pipelines and unhealthy Argo apps create findings; these do not authorize GPU interruption. A finding's first/last observation is retained while the condition persists. Pending recovery blocks further deletions rather than blindly retrying.

## Build and staged rollout

1. From repository root build `docker build -f research/ops_agent/Dockerfile -t rtl-ops-agent:20260914-v1 .`. Import the built image onto the control node's container runtime. Verify the copied providers source digest equals the coordinator's source.
2. Apply `admission.json` first and inspect policy `status.typeChecking` for warnings. It fails closed for this exact service account and disallows pod deletion outside approved namespace/app/ReplicaSet boundaries and GPU limits. RBAC cannot constrain dynamically generated pod names to a Deployment, so admission provides the additional boundary; the program verifies actual owner UIDs and replica health.
3. Apply `resources.json` with `DRY_RUN=true`. It mounts only four named model configuration keys, has dedicated SA/PVC, no Secret read API permission and no write RBAC. Confirm a successful observation, nonempty provider identity and persisted findings/audit. The default image is a local tag: pin its verified digest in the deployed manifest when publishing a production build.
4. Use an independent canary Deployment with two replicas, `app=rtl-ops-recovery-canary`, no GPU, one controlled unready pod and one healthy peer. Do not induce a failure in production. Add `recovery-rbac.json` after policy acceptance. First scope `RECOVERY_DEPLOYMENTS` to canary only, set `DRY_RUN=false`; optionally shorten `MIN_UNREADY_SECONDS` for canary. Verify the failed UID is deleted, its replacement becomes Ready, the healthy peer UID remains unchanged, pending state clears and status records recovery. Model calls are rate limited; wait for the next eligible plan rather than resetting live budgets.
5. Using server-side dry-run and impersonation, verify unrelated pods, GPU pods, training Job pods, Secret/PVC writes, deployment patching, exec and node actions are denied. An RBAC `can-i delete pods` yes is expected only in the two approved namespaces; actual admission denies nonapproved workloads. Never actually delete a protected pod to test this.
6. After these gates, expand `RECOVERY_DEPLOYMENTS` to the approved production list and retain `DRY_RUN=false`, default 600 seconds, cooldown and budgets. Commit exact desired manifests through GitOps and confirm Argo revision/sync plus another live observation. A singleton operator remains ineligible regardless of allowlist membership.

Run `python3 -B -m unittest research.ops_agent.test_agent`. Unit checks are not evidence of cluster permission enforcement, provider reachability, canary replacement or production activation; record each separately.

For accelerated isolated acceptance use the same SA and image but a separate Job, `STATE_DIR=/state/canary-acceptance-<unique-id>`, exactly `RECOVERY_DEPLOYMENTS=["rtl-brain/rtl-ops-recovery-canary"]`, `MIN_UNREADY_SECONDS=10`, `PLAN_INTERVAL_SECONDS=10`, `DRY_RUN=false`. Run one invocation to establish observation, wait at least 10 seconds, run a second invocation using the same isolated directory for a real LLM-selected recovery, then a third to observe replacement health. Creation age must also exceed 10 seconds. Use a separate directory for prior read-only acceptance; never reset the production state/budget to accelerate tests. The shorter planning interval is accepted only for the exact singleton canary allowlist; any production or mixed allowlist enforces at least 900 seconds. Production failure age remains at least 600 seconds and target cooldown remains 1800 seconds, including for the canary.
